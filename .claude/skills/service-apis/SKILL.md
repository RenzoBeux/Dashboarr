# Service API Documentation (sources of truth)

When implementing or debugging a service integration, consult the upstream API docs below — these are the authoritative references. Prefer fetching the relevant doc page over guessing endpoint shapes.

Live sessions via `/proxy/getSessions` pass the raw Jellyfin payload through. See `services/jellystat-api.ts`. |
| Autobrr | https://autobrr.com/api + route handlers in `internal/http/` and TS shapes in `web/src/types/*.d.ts` of autobrr/autobrr | Auth via `X-API-Token` header (`?apikey=` also accepted; we send the header). JSON is snake_case. `GET /api/healthz/liveness` is **anonymous** — it answers 200 with a wrong key, so the connection probe validates against `GET /api/release/stats` instead. Release search: `GET /api/release?limit&offset&q&push_status` (`PUSH_APPROVED`/`PUSH_REJECTED`/`PUSH_ERROR`; an invalid value 400s, so omit when unfiltered). **`GET /api/irc/network/{id}/restart` is a GET that mutates** — keep it in a mutation, never a query. Filter toggle: `PUT /api/filters/{id}/enabled` body `{enabled}`. See `services/autobrr-api.ts`. |
| Deluge | https://deluge.readthedocs.io/en/latest/devguide/how-to/curl-jsonrpc.html + `deluge/ui/web/json_api.py`, `deluge/ui/web/auth.py`, `deluge/core/core.py`, `deluge/core/torrent.py` of deluge-torrent/deluge | Web UI JSON-RPC v1: `POST <base>/json`, body `{method, params, id}` with **all three keys required** and params **positional only**. We target Deluge 2.x. **Everything answers HTTP 200** — failures live in `{error: {message, code}}` (1 = not authenticated, 2 = unknown method, 3 = local exception, 4 = daemon exception, 5 = malformed request). Auth is a single Web UI **password, no username**, exchanged via `auth.login` for a `_session_id` cookie (sliding 1h expiry); replay the raw cookie value rather than trusting a path-aware jar, because the cookie's `Path` changed in 2.2.0. **`Content-Type` must be exactly `application/json`** — Deluge <= 2.0.5 string-compares it and rejects the `; charset=utf-8` most HTTP stacks append. **THE trap: deluge-web is a proxy to a separate deluged daemon, and until it has connected every `core.*`/`label.*` call answers `Unknown method` (code 2)** — so a fresh session must run `web.connected` -> `web.get_hosts` -> `web.connect(hostId)`, and any later code 2 (or a code 3 `AttributeError: 'NoneType'`) means the daemon went away and the handshake must be redone. `web.connect` fails SILENTLY (returns null with `error: null`), so verify its result is a non-empty method array. **Never send an empty `keys` list** to `core.get_torrents_status` — Deluge reads that as "every field" and returns files/peers/pieces for every torrent. Numeric traps: `progress` is **0-100** (but is pinned to 100 whenever `state` is `Error`, so recompute from `total_done`/`total_wanted` there), `file_progress` is **0-1**, `ratio` is `-1` for "nothing downloaded", `eta` is seconds with 0 = unknown and -1 = over a year, and `max_download_speed`/`max_upload_speed` are **KiB/s where any NEGATIVE value is unlimited and 0 is a real throttle**. `state` is one of Allocating/Checking/Downloading/Seeding/Paused/Error/Queued/Moving — there is **no Stalled** (that's Downloading at a zero rate) and **no turtle/alt-speed mode anywhere**. `pause_torrents`/`resume_torrents` take a list, but calling them with NO argument pauses the whole session; `remove_torrents` returns an **empty list on success** and `[[id, error]]` pairs on partial failure. Code-4 messages are a stringified Twisted `Failure` wrapping the real class and traceback — unwrap it before showing a user. Labels are an optional plugin (`label.*`), single-valued, and `label.add` lowercases while `label.set_torrent` does not. See `services/deluge-api.ts`. |
| Cleanuparr | https://cleanuparr.github.io/Cleanuparr/docs/configuration/stats (v2 stats) + C# controllers in `code/backend/Cleanuparr.Api/` of Cleanuparr/Cleanuparr | Auth via `X-Api-Key` header (or `?apikey=`); the key authenticates as a full user on EVERY `[Authorize]` controller (jobs, events, stats), not just stats. Anonymous `GET /health` is **root-mounted** (not under `/api`), so `apiBasePath` is empty and module paths self-prefix `/api` (JellyStat pattern). **v1 `/api/stats` is sunset 2026-09-01 — use `/api/v2/stats?hours=` only.** JSON is camelCase properties but **PascalCase enum strings** (`JsonStringEnumConverter`, no naming policy), and zero-activity breakdown keys are omitted, never sent as 0. `GET /api/events?page&pageSize&severity&eventType&search` → `{items,page,pageSize,totalCount,totalPages}`. `POST /api/jobs/{jobType}/trigger` — **`Seeker` refuses manual triggers (400)**. See `services/cleanuparr-api.ts`. |

Notes:
- **Bindery diverges from the *arr family in ways that bite.** All verified against `vavallee/bindery@main`:
  - **Auth.** One install-wide API key. `X-Api-Key` always works; `?apikey=` is honoured on **GET/HEAD/OPTIONS only**. API-key requests bypass both the `X-Requested-With` and CSRF guards, so mutations need no extra headers. `/api/v1/health` is on the server's unauthenticated allowlist and answers 200 without a key — probe `/api/v1/system/status` instead, or a wrong key reads as healthy.
  - **Three envelope shapes in one API.** `{items,total,limit,offset}` on `/author`, `/book`, `/history` (paginate by **offset**, never `page`; `limit` above 500 is silently clamped and echoed back, so advance by what you received); `{items,partial?,staleClients?}` on `/queue`; a bare array on `/wanted/missing`, `/rootfolder`, `/qualityprofile`, `/metadataprofile`, `/blocklist`, `/pending`, `/indexer`. `/history` already changed from bare array to envelope once. `lib/bindery-normalize.ts` absorbs all of them.
  - **`GET /book?authorId=N` silently drops every other filter.** That branch honours only `authorId`, `includeExcluded` and in-memory limit/offset — `status`, `search`, `sort`, `mediaType`, `monitored` and the release bounds are ignored, and it orders by release date rather than title. It still answers 200, so the bug is invisible. Use the embedded `books[]` on `GET /author/{id}` instead.
  - **`availableBookCount` and `wantedBookCount` are always 0.** `AuthorStats` is built in exactly one place (`internal/db/authors.go`) which sets `bookCount` alone. `statistics` is also present only on the LIST response; `GET /author/{id}` omits the key. Any progress bar derived from those two fields reads 0% or 100% for every author forever.
  - **`editions[]` is dead on the wire.** `models.Book` declares it, but no handler populates it and there is no `/book/{id}/editions` route. `bookFiles[]` and `identifiers[]` (single-book reads only) are the real data.
  - **Partial updates are safe.** `PUT /author/{id}` and `PUT /book/{id}` decode every field as a pointer and apply only what is present — send just the changed field. Two consequences: JSON `null` is indistinguishable from omission, so a profile **cannot be cleared** (only `audiobookRootFolderId`, via `clearAudiobookRootFolder`); and sending `title`/`description`/`genres`/`language`/`releaseDate` also **locks that field** against metadata refresh, so never include them in a monitor toggle.
  - **Images.** `imageUrl` is a relative proxy path, `<BINDERY_URL_BASE>/api/v1/images?url=<encoded remote>`, on both list and detail responses. Rebuild it from the embedded `url=` param rather than passing it through, or a subpath deploy double-prefixes. Queue rows, `/wanted/missing` and `/search/*` stubs are **not** proxied.
  - **Absent entirely:** `/command`, `/calendar`, `/diskspace`, `/tag`, `/queue/details`, `/release`, `/wanted/cutoff`, an *arr-style `/health` issue array, and SignalR/websockets. `/queue` takes no query parameters at all. There is no blocklist option on any queue-removal route.
- **Servarr `POST <provider>/testall` answers 400 on the happy path.** `ProviderControllerBase.TestAll()` (shared by Radarr/Sonarr/Lidarr/Prowlarr's indexer, downloadclient, applications, importlist and notification controllers) ends with `return result.Any(c => !c.IsValid) ? BadRequest(result) : Ok(result);` — so whenever any provider fails its test you get `400` **carrying the full result array**, not an error envelope. Treat that body as the outcome (`[{ id, isValid, validationFailures: [{ propertyName, errorMessage }] }]`) instead of an HTTP failure, and resolve `id` → name with a GET on the same route minus `/testall`. See `services/arr-health.ts`.
- **NZBHydra2's wire format has several traps, and its wiki is stale.** All verified against `theotherp/nzbhydra2@master`:
  - **The two halves of the API fail in completely different ways, and the split is not obvious.** `/api` (the newznab mount, `ExternalApi`) answers **HTTP 200 for every error**: its `@ExceptionHandler` returns a `NewznabXmlError` with the default 200 status, so a wrong key comes back as `{"code":"100","description":"Wrong api key"}`, never a 401 — the probe and the search path must read the BODY. But `/api/stats*` and `/api/history/*` live in `ExternalApiStats`, a **separate `@RestController` that inherits none of that** (`@ExceptionHandler` is controller-local, and the project's one `@ControllerAdvice` lists only Spring's own exception types), so their `IllegalAccessException` reaches no handler and Tomcat renders a stock **`500 text/html`** page. Verified against 8.9.0: wrong key on `/api?t=caps` → 200 JSON error envelope; wrong key OR `allowApiStats: false` on `/api/stats/indexers` → 500 HTML. Because the body is HTML, `serviceRequest` surfaces it as an `AuthProxyResponseError`, so anything classifying that failure has to key on `status`, not the message. `readHydraJsonError` / `readHydraXmlError` handle the 200-envelope half; `isStatsApiGated` handles the 500 half.
  - **Newznab JSON attribute holders come back under EITHER `"@attributes"` or `attributes`.** Upstream declares `@JsonProperty("@attributes")` on `NewznabJsonItemAttr`, `NewznabJsonEnclosure`, `NewznabJsonChannelResponse` and `CapsJsonServer` — but the **GraalVM native build loses the rename** and emits the bare field name. Both mainstream Docker images (hotio and linuxserver) ship that native binary, so `attributes` is what a containerised instance actually sends; verified on 8.9.0, where `t=caps` answers `server.attributes.appversion` and a search answers `channel.response.attributes`. Reading only one spelling type-checks against a hand-written interface and fails **silently**: every row's indexer name falls back to "NZBHydra2" and every size reads 0. Go through `hydraHolder()` in `lib/nzbhydra2-normalize.ts`, which accepts either.
  - **Since v7.15.3 (2025-07-04) `/api/stats`, `/api/stats/indexers`, `/api/history/searches` and `/api/history/downloads` take `@RequestBody`** — a JSON body is mandatory and query params are ignored. The wiki still documents only the old query-param/dot-notation form. We send the key BOTH ways so pre-7.15.3 installs keep working.
  - **Those four are also gated by `auth.allowApiStats`** (default `true`). With it off they reject a valid key while `t=caps` keeps working — so a failure there means "the user switched the stats API off", not "wrong key". It is indistinguishable from a wrong key at the HTTP level (both are the 500 above), which is why `isStatsApiGated()` is only consulted alongside a caps query already known to have succeeded.
  - **Timestamps are polymorphic.** `application.properties` sets `write-dates-as-timestamps=false`, yet upstream's own UI (`parseAppTimestamp` in `core/ui-src/js/indexer-statuses-controller.js`) accepts a raw number (epoch **SECONDS**, e.g. `1544551917.589`), a numeric string, and an ISO-8601 string for the same field — and a real 8.9.0 answers `/api/stats` with `"after": 1785283200.000000000`, i.e. decimal epoch seconds, so the property does not win. Send ISO-8601 for `after`/`before`. `parseHydraTimestamp` absorbs all three.
  - **`request.sortModel` is mandatory on the history endpoints.** `History.getHistory` guards its first sort branch with `if (sortModel != null)` and then dereferences `sortModel.getColumn()` unconditionally on the next line, while `HistoryRequest.sortModel` has no default — omit it and the call NPEs into a 500 (measured: with it, 200 + the `Page` envelope; without it, 500). `sortMode == 1` is ASC; **every other value, 0 included, is DESC**. `filterModel` does default, so it is safe to omit. `sortModel.column` is interpolated straight into native SQL, so only send whitelisted names.
  - **History paging is asymmetric**: the request `page` is 1-based (`PageRequest.of(page - 1, limit)`), the response `Page.number` is 0-based — so the next page is `number + 2`.
  - **`/api/stats` is expensive** — upstream aborts the calculation at 30 s, so give it a longer timeout and request only the flags you render. **Never omit `request`**: `ApiStatsRequest`'s no-arg constructor turns nearly every flag on. Naming trap: the request flag `avgIndexerUniquenessScore` populates the response field `indexerScores`.
  - **`/actuator/health/ping` is `permitAll`** (and `management.endpoints.web.exposure.include=*`), so it is a fine reachability ping but can never validate the key — the same trap as Autobrr's `/api/healthz/liveness`. Verified 200 on 8.9.0.
  - **`searching.wrapApiErrors`** (default `false`) makes an internal error return an *empty but valid* search result at 200, byte-identical to a genuine zero-result search. There is no way to tell them apart; the empty-state copy says so rather than the code guessing.
  - `indexers=` matches indexer **names**, not ids (`/api/stats/indexers` exposes no id at all). `o` defaults to **XML** — `o=json` is required. `limit` defaults to 100 and is capped at 100. Search result `link` is `<hydraUrl>/getnzb/api/<id>?apikey=<key>`, i.e. self-authenticating, but the download client has to be able to reach that host.
  - With auth configured AND `restrictSearch` + `restrictStats` + `restrictAdmin` all on, `HydraAnonymousAuthenticationFilter` grants no authorities and even `/api` demands HTTP Basic. Per-instance custom headers are the escape hatch.
- The `backend/dashboarr-backend/` Node.js service is in-tree and not a third-party API — its surface is whatever we define there.
- Where an instance hosts its own OpenAPI/Swagger (Radarr, Sonarr, Prowlarr, Bazarr, Jellyfin), prefer fetching the live spec from a real instance over the public docs when verifying field types or new endpoints — the live spec matches the running version exactly.
